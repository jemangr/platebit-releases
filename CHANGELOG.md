## 2.3.4 (146)
- Version 2.3.4: phone `versionCode` 146, watch 1000146, watch faces 2000146, all "2.3.4".
- Fix: the AI coach sometimes said a meal was logged ("accepted") with no card to tap. The model copied the history note `[Proposed change: …: accepted, done]` instead of writing an `<actions>` block, and the parser dropped blocks in code fences, with curly quotes, trailing commas, escaped or singular tags, portion totals instead of per-100 g values, or a cut-off array. The history note now reads `[Earlier card "…", accepted by the user]` and the prompt forbids writing it; copied notes are stripped from the text; the parser takes all those shapes (whole objects kept from a cut-off array); an answer that meant to propose but gave no card is asked once more for the block, and if it still fails the user reads "I couldn't prepare that" instead of a false "done". Tests: `CoachProbeTest`.

## 1.74.0 (130)
- Version 1.74.0: phone `versionCode` 130, watch 1000130, watch faces 2000130, all "1.74.0".
- Open on computer (Me → Data, `pc/`, `ui/settings/PcLiveUi`): a foreground service (`PcLinkService`, type `connectedDevice`, `FOREGROUND_SERVICE_CONNECTED_DEVICE` and `CHANGE_NETWORK_STATE`, `stopWithTask`, never restarted) runs a small HTTPS server on the phone's Wi-Fi IPv4 address only (NanoHTTPD 2.3.1, the one new dependency; port 8443, another when taken), TLS 1.2/1.3 only, never compressed, at most 24 connections and 2 KB bodies. The screen shows `https://<address>:<port>`, a 6-digit code and the certificate's SHA-256 fingerprint, with "Don't use this on public Wi-Fi"; the ongoing notification says "Computer connected" with Stop. No network call to the internet.
- The certificate (`PcCert`): an ECDSA P-256 key and a self-signed X.509 v3 server certificate built on the phone (397 days, serverAuth, names localhost, 127.0.0.1 and the address at the time), kept in `pc_link_cert.json` encrypted with the app's file key (in memory only without one), made again a week before it runs out; never in backups or the move.
- Pairing (`PcPairing`): the code works once (compared in constant time); 5 wrong tries lock it until a new code; a new code disconnects the computer before, so one computer at a time and a new code for every connection. The session is a random token in a `__Host-platebit` cookie (HttpOnly, Secure, SameSite=Strict, Path=/), valid only from the address that paired, with its own write token (`X-Platebit-Csrf`).
- The API (`PcApi`, tested without the server): `/` (the page, no data, its script by nonce), `/api/session`, `/api/pair`, `/api/data` (`PcExport.Data` v1, live), `/api/events` (Server-Sent Events: `changed` when the phone's plan, list, diary, weight, workouts, women's health or activity change, a ping every 20 s), `/api/plan` (another, lock, unlock, approve, unapprove), `/api/shop` (tick, untick, add, remove an own item), `/api/logout`. Other host names get 421 (no DNS rebinding); writes need the session, the token, `application/json` and the same origin; every field is checked (ops, slots, ISO dates, string fields only, no extra fields), then again by `PcPhoneBackend` against the phone's data through `MealPlanOps` and `GroceryTicks`, as on the screens (a locked meal isn't swapped; only the days shown, from today; ticks only for items on the list). Headers: `Cache-Control: no-store`, nosniff, no referrer, no framing, the live page's CSP (`script-src 'nonce-…'`, `connect-src 'self'`).
- Auto-stop (`PcAutoStop`): 15 minutes without a request (the event stream doesn't count), the Wi-Fi it started on lost or its address changed (a network callback), Stop, Platebit swiped away, or the process ending.
- Never on the computer: AI keys, backups, erase-all, medicines, notes, the privacy and coach-sees switches. Women's health only after the user unlocks it on the phone in that session (fingerprint, face or screen lock), never in discreet mode (hidden card, neutral reminders or the lock), checked again at each request.
